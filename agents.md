# Agent guide: uBlockFox

This file is the working contract for agents changing this repository. Read it
before editing code. It describes the product boundary, the refactor goal, the
invariants that define behavioral equivalence, and the validation workflow.

---

## 1. Product boundary

uBlockFox is **uBlock Origin for native Firefox 160+**.

Non-negotiable product facts:

- Product name stays `uBlock Origin`.
- Extension ID stays `uBlock0@raymondhill.net`.
- Firefox floor stays `160.0`.
- Runtime stays **Manifest V2** with a real background page.
- The only build/publish target is `make firefox`.

There are no Chromium, Edge, Opera, Safari, Thunderbird, MV3, uBO Lite, or other
browser targets. Do not add cross-browser abstraction layers or revive unused
platform code. The remaining `vAPI` modules are Firefox capability shims used by
the shared uBO core; the guards inside them cover Firefox desktop/Android API
differences, not other browsers.

Do not change:

- `manifest.json` identity, minimum version, MV2 background page, or permissions
  unless a separate, explicit product decision asks for it.
- The Firefox-only build scripts in `tools/make-firefox.sh`.
- The fact that request blocking is done by the MV2 static/dynamic filtering
  engines. The `SNFE: DNR` export is diagnostic only, never an MV3 runtime path.

---

## 2. The golden rule

> The goal is **function-preserving refactors**: same engine decisions and
> outputs, just less work per request and a more Firefox-native shape.

This rule applies to the whole codebase. There is no "protected area only"
exception. A sensitive-looking file is not automatically off-limits; it is
changeable when equivalence is proven. The test is **observable equivalence**,
not file location.

A good batch:

- keeps the same filtering decision for every request;
- keeps the same strings, bytes, ordering, and mutation side effects;
- removes allocations, repeated parsing, repeated lookups, or listener churn;
- uses shapes and loops that SpiderMonkey/Warp handles predictably;
- is small enough to validate in one Firefox smoke run.

Prefer 2-4 related files per batch. Examples of accepted directions:

- replacing `forEach`/`map`/`filter`/`flatMap` chains with direct loops;
- reusing scratch arrays, sets, and option objects across synchronous calls;
- constructing objects with their final shape instead of growing them with
  `??=` or later assignments;
- hoisting constant wrapper fragments, sentinels, and option fragments;
- batching lookups that previously repeated token walks or register setup;
- avoiding `Object.assign()`, spreads, and temporary arrays in hot paths when
  the same insertion order can be built directly.

Do not perform drive-by cleanup. If a change is not function-preserving or does
not reduce work / improve Firefox-native shape, do not include it.

---

## 3. What "Firefox-native" means here

This is a WebExtension. SpiderMonkey, WarpJIT, Gecko networking, GeckoView, and
browser C++ patches cannot be shipped in the XPI from `make firefox`.

Firefox-native extension work therefore means:

- use Firefox's MV2 `webRequest`, `webNavigation`, `tabs`, `contentScripts`, and
  `filterResponseData` APIs directly;
- keep Monarch/SpiderMonkey-friendly JavaScript: stable hidden classes, monomorphic
  call sites, direct property writes, direct loops, fewer short-lived objects;
- avoid repeated `new URL()`, repeated regex compilation, repeated string
  concatenation in loops, and repeated array materialization;
- keep listener registration and event dispatch order exactly as before;
- use the native `world: 'ISOLATED'` / `world: 'MAIN'` registration path and its
  fallback wrapper path without changing generated bytes.

Ideas that require browser internals belong upstream in Mozilla, not in this
repository. Record them as notes if needed, but keep the shipped extension
behavior unchanged.

## 4. Invariants that must stay byte-for-byte or behavior-for-behavior

### 4.1 Identity and runtime

- Product name `uBlock Origin`.
- ID `uBlock0@raymondhill.net`.
- Manifest version `2` with background page ending in `/background.html`.
- `strict_min_version` `160.0`.
- No MV3 runtime, DNR enforcement, or uBO Lite behavior.

### 4.2 Flavor and compatibility surfaces

- `vAPI.webextFlavor` must stay dynamic. Never hoist flavor checks into immutable
  module-load constants.
- Preserve `modifyWebextFlavor` and all hidden compatibility settings.
- Preserve parser environment tokens, including historical browser tokens such as
  `env_chromium`. They affect filter-list preparsing, not browser support.
- Preserve Firefox Android guards in `platform/common/vapi-background.js` and
  elsewhere.
- Preserve DNS/CNAME handling.
- Preserve request suspension and `filterResponseData` semantics.
- Preserve DNR diagnostic export context and output. It is not a runtime path.
- Preserve logger and inspector output, including log data order and realm.

### 4.3 Network filtering

- Preserve `filterQuery(fctxt, 'removeparam')` semantics and the public
  `matchAndFetchModifiers(fctxt, modifierName)` API.
- Preserve redirect, `removeparam`, `uritransform`, `urlskip`, CSP, and permission
  modifier decision order.
- Preserve `details` object mutation exactly. Do not replace deliberate mutation
  with copies unless equivalence is proven.
- Preserve `try { await native(...) } catch {}` behavior. Do not replace it with
  `.catch()` where a synchronous throw must stay swallowed.

### 4.4 Scriptlets and generated source

These outputs are observable and must remain byte-identical unless a change is
proven to produce identical bytes:

- generated scriptlet source strings;
- `/* n */` comment counts;
- scriptlet/core/framework wrapper text;
- world order and native registration/unregistration order;
- secret substitution;
- `ArglistParser` injected source.

Specific rules:

- Keep `ArglistParser` helpers inside the class body. The class is injected via
  `fn.toString()`.
- Do not touch either `hashFromStr()` copy.
- Do not modify `src/js/scriptlet.template.js`,
  `src/js/scriptlet-begin.template.js`, `src/js/scriptlet-end.template.js`, or
  `src/js/resources/scriptlets.js` unless generated bytes are provably identical.
- Do not change fallback wrapper text, including the `earlyBailoutCode` marker and
  its split halves.
- Keep the `userCSS` port path in the content script unchanged. Only the
  background-side CSS API handling was made Firefox-native.

### 4.5 Cosmetic filtering

- Preserve selector cache insertion/eviction order.
- Preserve procedural/declarative selector output order.
- Preserve specific vs generic cosmetic filtering flags and exceptions.
- Preserve `getContentScripts()` plain and rich option shapes.

### 4.6 Events and ordering

- Preserve the order of `frameManager` listener dispatch.
- Preserve `before-tab-created`, `tab-created`, `before-frame-committed`,
  `frame-committed`, `tab-updated`, `frame-removed`, and `tab-removed` event order.
- Preserve native scriptlet registration and unregistration order: MAIN then
  ISOLATED where applicable.

## 6. Batch workflow

The user will usually issue one of these commands:

- `commit` — commit the current uncommitted batch and stop.
- `next` — implement the next function-preserving Firefox-native batch.
- `commit then next` — commit the current batch, then implement and validate the
  next batch.

Rules:

1. Commit only the files in the current batch.
2. Use a concise imperative commit message, for example
   `Use direct extended filter scans`.
3. Keep commits local. Do **not** push unless explicitly asked.
4. After `next`, report the changes, validation results, and the exact uncommitted
   file list.
5. Do not reintroduce deleted harness files, Selenium/check gates, or npm test
   gates. Temporary validation harnesses are allowed but must be removed before
   reporting completion.

## 7. Validation checklist

Run all applicable checks for every batch:

```bash
node --check <each modified .js file>
git diff --check
npm run lint
make firefox
```

`make firefox` is the only build target. A `Nothing to be done for 'firefox'.`
result is fine when the build is already current.

For behavior-affecting batches, also run a one-off differential Firefox 160+ smoke:

- Build/copy the baseline from committed `HEAD` (or the current known-good build)
  before editing.
- Inject temporary probe scripts only into the copied build, never into tracked
  source.
- Use `/Applications/Firefox.app/Contents/MacOS/firefox` and
  `/opt/homebrew/bin/geckodriver` when available.
- Compare normalized output. Normalize at minimum:
  - UUIDs in `moz-extension://...` URLs;
  - local server ports;
  - generated `zeta_[0-9a-f]{32}` secrets.
- Compare bytes and ordering, not just counts: generated scriptlets, option key
  order, event order, listener order, registration order, and returned arrays.
- Remove all temporary harnesses, baselines, generated scripts, and profile
  directories after validation.

Never weaken validation by adding a permanent test gate to the repository just to
make a batch pass.

## 8. Review checklist before reporting a batch

Ask these questions before saying a batch is done:

1. Did any generated string, comment count, or registration order change?
2. Did any listener/event/store mutation change?
3. Did `vAPI.webextFlavor` become a module-load constant? No.
4. Did a `try/catch` become a `.catch()` that changes synchronous throw behavior?
5. Did an object gain or lose enumerable fields in a path where consumers inspect
   or serialize it?
6. Did a compatibility setting, hidden setting, parser token, Android guard, or
   diagnostic export disappear?
7. Is the batch limited to 2-4 related files with one smoke covering them?
8. Are all temporary validation files deleted?
9. Is the working tree state exactly what the report says?

If any answer is uncertain, rebuild the differential harness and prove
equivalence before reporting completion.
